FINDING — triaging the FRESH failures today's A/B produced (2026-07-24, model-free)
==============================================================================

WHY THIS FILE: yesterday's gate-mining ended on a negative result — re-mining the archived
_fail-* backlog yields no new clean gate, because the chain has grown to cover it. The
meta-insight was that NEW gate shapes come from NEW failing runs. Today's scaled A/B produced
exactly that: fresh, never-before-seen failures on shortener and taskapipro. This triages them
and records which are gate-able and which belong to the model. No model calls needed.

1. taskapipro, fleet arm's LAST remaining failure — a SELF-CONTRADICTING TEST
   internal/store/memory_test.go TestListProjectsSorted:
       projects := []models.Project{{ID:"p2",Name:"z"}, {ID:"p1",Name:"a"}}   // creation order
       ... create both ...
       got, _ := store.ListProjects(ctx)
       for i := range got { if got[i].ID != projects[i].ID { t.Errorf(...) } }
   The IMPLEMENTATION IS CORRECT: ListProjects does sort.Slice by ID ascending, which is what
   the spec demands ("list id-sorted"). The TEST is wrong — it compares the sorted result
   element-wise against the UNSORTED seed slice. A test whose own name says "Sorted" asserts
   creation order. Failure text: `got {p1 a}, want {p2 z}` and `got {p2 z}, want {p1 a}` —
   the tell-tale symmetric swap of a sorted-vs-insertion-order comparison.

   GATE DECISION: NO GATE. The repair is "sort the EXPECTATION slice by the same key the
   implementation sorts by", which requires inferring the key from another file. That is an
   inference, not a single meaning — the same line the arity/value-guess tail was refused on.
   A wrong key still compiles and fails an assertion, i.e. it would masquerade as a model
   logic bug and MISLEAD the fix loop. This belongs to the model.

   PREDICTION (falsifiable, for the running 16-round arm): this failure is likely REPAIRABLE
   by more rounds rather than by a gate or a bigger fleet. The 8-round arm ended while still
   producing NEW error surfaces (extension round 10), and the fix loop targets by error
   location — which points squarely at the test file. If the 16-round arm goes green, the
   published "raise the ROUND budget before enlarging the fleet" recommendation is supported;
   if it stalls on this same test, the recommendation is wrong and the failure is model-shaped
   in a way rounds do not fix.

2. taskapipro, BASE arm's terminal failure — CROSS-FILE CONTRACT MISMATCH
   internal/service/service.go:41 `return s.store.CreateTask(ctx, t)` where the store returns
   `error` and the caller wants `(models.Task, error)`. Base never moved off it in 11 rounds.
   GATE DECISION: NO GATE. Both sides are locally valid Go; "which side is wrong" is a design
   choice, not a mechanical repair. Confirmed empirically that this is model-shaped and
   model-fixable: the fleet resolved it by rewriting the caller to match the store.

3. shortener, BASE arm's terminal failure — SEMANTIC TEST ERROR
   The test JSON-decoded the body of a 301 redirect (`GET /r/{code}`) and read .Hits from it;
   the endpoint has no body, so Decode returns EOF. The spec states the correct shape
   explicitly. GATE DECISION: NO GATE — a gate would have to know that /r/ is a redirect and
   that hits come from /stats/, i.e. read the spec's semantics. The fleet fixed it.

SUMMARY: three fresh, genuinely distinct failure shapes, and NONE of them yields a clean
single-meaning gate. All three are semantic or design-level. That is a second, independent
confirmation of the gate campaign's stopping condition — not because the backlog was already
covered (yesterday's argument), but because the failures that REMAIN at this maturity level
are the kind gates must not touch. The deterministic chain has taken the mechanical tail; what
is left is model work, which is precisely why routing showed measurable value today.

COUNTERPOINT, so this is not read as "gates are done": the control experiment in
RESULT-fleet-ab.txt shows a gate (_fix_external_test_package) beating routing outright on the
failure it covers — 1 round, 11s, no second model, on a failure that had defeated two models.
When a single meaning exists, a gate is still strictly the better tool. The rule stands:
gates for mechanical single-meaning repairs, routing for the semantic residue.

PREDICTION OUTCOME (item 1) — RESOLVED, and my prediction was WRONG
  I predicted the ListProjectsSorted failure was "likely REPAIRABLE by more rounds". The
  16-round arm was run: 2/3 again, stopping on the SAME two tests (TestListSorted and
  TestListProjectsSorted) with "error surface repeats". Nine extra rounds moved it zero.
  So the failure is a stable FIXED POINT across rounds AND across all three fleet members —
  the strongest form of "model-shaped" available: not one model's blind spot, but a shape all
  of them re-derive identically. The gate decision above (NO GATE, the sort key must be
  inferred) is unchanged, but the reason it matters is now sharper: nothing else this project
  has fixes this class either, so if a single-meaning gate form is ever found, it would be
  worth real effort — this is the residue after both rounds and routing are exhausted.

THE THIRD LEVER (spec/prompt) PROBED CHEAPLY — UNRELIABLE, not a fix
  With rounds and routing both exhausted, the remaining lever was the spec/prompt. Testing
  that with a full taskapipro build costs ~3h; instead a 2-minute single-prompt A/B asked the
  7B base for just TestListProjectsSorted, forcing the REAL conditions (seed p2 then p1, i.e.
  reverse id order), with and without an explicit instruction that the expected slice must
  itself be sorted.
    ARM A (no instruction)  -> reproduced the bug EXACTLY: it even checks
        sort.SliceIsSorted(listed...) correctly, then loops comparing the sorted result
        element-wise against the CREATION-order seed slice.
    ARM B (explicit instruction) -> ALSO WRONG, in a new way: it sorted the RESULT (already
        sorted) instead of the expectation, then reflect.DeepEqual'd it against {p2, p1}.
  An earlier, less-forced phrasing of the same instruction DID produce the correct code
  (it sorted the expectation). So the prompt lever is UNRELIABLE here, not useless: the model
  has a strong prior to "sort something" and attaches it to the wrong operand under pressure.

  WHY THIS MATTERS FOR THE FIXED POINT: the failure is not "the model does not know the list
  is sorted" — Arm A explicitly ASSERTS sortedness one line before contradicting itself. It is
  a local inconsistency the model cannot see, which is exactly why re-running it (more rounds)
  and re-asking a stronger model (routing) both reproduce it.

  A NARROW GATE DOES BECOME VISIBLE, and is still declined: in Arm B's shape the comparator
  IS present in the test file (`sort.Slice(projects, func(i,j) { ID < ID })`), so "sort the
  literal expectation by the same comparator" would need no cross-file inference. But the REAL
  taskapipro failure has no sort in the test at all — the key lives in memory.go — so the gate
  would cover the probe's shape and miss the actual one. Declined: a gate that fires only on
  the variant you synthesised is worse than none.

  METHOD NOTE — the probe's FIRST version was broken and reading the output caught it: its
  verdict function only matched quoted ID literals (so it called an integer-ID answer
  "unparseable"), and worse, its control arm seeded in ALREADY-ASCENDING order, which masks
  the bug entirely. A control that cannot fail cannot isolate anything. Forcing the reverse
  seed order is what made the comparison real.

4. shortener's degenerate GENERATION (base emits a repeated-digit string to max_tokens) —
   NO BUILDER FIX NEEDED, checked by reading the code, not assumed.
   This looked like a candidate for a new deterministic improvement (the session's rule: new
   failures yield new gates). Reading src/builder.py _sample_clean shows it is ALREADY handled:
   the degenerate draw fails extract/parse, why_dirty() returns "does not parse", the draw is
   rejected, and best-of-N resamples it (candidates=3 avoided it entirely — 9 parse-rejects ->
   1). At candidates=1 there is no resample, but that is the documented best-of-N contract, not
   a bug; the fix is "raise --candidates", a config choice. The shortener regression was the
   INTERACTION of candidates=1 with escalation timing (the file is handed off before base
   finishes), both existing known behaviors — not a generation defect. So there is no clean,
   single-meaning builder change to extract here. Recorded so the next session does not
   re-investigate it: the generation machinery is correct; do not add a redundant degeneracy
   gate on top of the parse check.
