RESULT — fleet routing at PROJECT scale: base-only vs base-first fleet (2026-07-24)
==============================================================================

THE QUESTION THIS ANSWERS
  go_dev_bench proved an ORACLE ceiling: no single model beats the base (44/48), yet a
  {base, go-dev-final, go-dev-14b} union solves 48/48. realizable_router.py then tempered
  it: a compile/vet-gated router captures ZERO of that +4, because the base's wrong answers
  COMPILE. The open question was whether the Builder — whose gate is build+vet+TEST, i.e. a
  real test signal, the thing the bench lacked — converts the ceiling into a real win on a
  whole multi-file project. Everything before this was unit-task or plumbing-level.

DESIGN (what makes this causal, not anecdotal)
  Same spec, same 8-round budget, same base model and port for member 0 in both arms; the
  ONLY intervention is whether --fleet is passed. The coder is deterministic per
  (prompt, temperature), so the two arms are BYTE-IDENTICAL until an escalation fires —
  every file that ends up differing is the routing's own footprint.

RESULT — specs/shortener.yaml (the family with 14 archived historical failures)
                      score       stages                   escalations   wall
    base-only         2/3  RED    build+vet ok, TEST FAIL      0          719s
    base-first fleet  3/3  GREEN  build+vet+test ok           12         1174s
  Independently re-verified outside the harness: `go test ./...` -> ok (fleet), FAIL (base).
  Base exhausted its whole budget (9 rounds incl. extensions) and stayed red. 5 source files
  diverged (codec.go, handlers.go, router.go, store.go, shortener_test.go); go.mod and
  main.go stayed byte-identical.

  ==> ROUTING CONVERTED A BUILD THE BASE COULD NOT COMPLETE INTO A GREEN ONE. This is the
  first project-scale evidence for the thesis's algorithm term: same base model, same
  budget, the only difference is that stuck files get handed to another member.

WHAT THE BASE COULD NOT FIX (the rescue, concretely)
  TestStatsCountsOneHit: the base wrote a test that JSON-decodes the response of
  `GET /r/{code}` into a Link and reads .Hits from it. But /r/{code} is a 301 REDIRECT with
  no body, so Decode returns EOF — and the spec SPELLS THIS OUT ("then GET /stats/+code",
  and it even warns a fresh link would read 0, not 1). The base re-wrote that same wrong
  test through NINE rounds. After escalation the file came back structurally correct:
  assert rec2.Code == http.StatusMovedPermanently, then read Hits from /stats/.
  This is the model-shaped tail the gate campaign deliberately refused to gate (a gate would
  have to GUESS semantics) — precisely the residue routing is supposed to absorb.

THE HONEST OTHER HALF — ESCALATION IS NOT MONOTONE
  Both arms independently hit the same codec bug (Encode emits least-significant digit
  first, so Encode(62)=="01" not "10" — again explicitly warned about in the spec). The
  BASE repaired it on its own. In the fleet arm codec.go had been escalated, and the bug
  SURVIVED rounds 4 and 5 under the specialist before later rounds recovered it. So handing
  a file to another member can LOSE a repair the base would have made; the net sign is a
  measurement, not a guarantee. Here it netted positive (red -> green), but a fleet is a
  trade, not a free upgrade.

COSTS AND LIMITS (stated, not buried)
  - Wall clock: 1174s vs 719s (+63%) — the 14B member's generations dominate. Routing is
    "nearly free" only while the base carries most files; on a hard spec it is not.
  - N=1 spec here. taskapipro (16 archived failures) is the second data point.
  - Once the first escalation fires the arms' error surfaces diverge, so this is a single
    causal A/B (intervention = routing), NOT a per-file ablation of which member fixed what.
    The per-file attribution above is read off the artefacts, not from a controlled ablation.
  - Escalation granularity: when the fix loop WIDENS to package-wide repair, every file in
    the widened set accumulates its own stuck-counter, so escalation goes fleet-wide (12
    escalations here) rather than staying targeted. Cheaper, more surgical escalation is an
    open improvement, not a validated one.

MEASUREMENT INTEGRITY — READ THIS BEFORE REPRODUCING
  The first attempt at this A/B was INVALID and was thrown away: mlx_lm.server silently
  ignores --adapter-path (FINDING-serving-adapter-noop.txt), so the "specialist" members
  were the plain base and the fleet was base->base->14B-base. Caught by a pre-flight control
  (same prompt to two ports must not return byte-identical text) BEFORE any number was
  believed. The numbers above were produced with serve_adapter.py, whose output was verified
  byte-identical to mlx_lm.load(..., adapter_path=...) ground truth. Run
  `check_serving.py <ports>` before any served A/B; had this gone unnoticed it would have
  reported "routing does nothing" — the expected result, for a completely spurious reason.

A PREDICTION I GOT WRONG (recorded because the miss is the informative part)
  Before this arm finished I predicted it would likely FAIL to build or oscillate, reasoning:
  shortener's blocker was INTRA-file (one badly written file — a better model fixes it in
  isolation), whereas taskapipro's was a CROSS-FILE CONTRACT MISMATCH, and FleetCoder
  escalates per FILE while the fix loop repairs one file at a time against the error text. A
  stronger model still sees only that file, so it could equally well "fix" either side and
  flip back next round.
  WHAT ACTUALLY HAPPENED: the fleet picked a side consistently and advanced two whole stages
  (no build -> build+vet). So routing helps on cross-file contract errors MORE than the
  per-file mechanism suggests. The mechanism I reasoned about was right; the conclusion was
  wrong, because a one-file repair is enough when the model chooses the direction that matches
  the rest of the codebase — and that choice is exactly a model-quality question, which is
  what escalation changes. Base failed it 11 times; escalated members got it.
  LESSON: "the loop reasons one file at a time" bounds the MECHANISM, not the OUTCOME.
  Per-file escalation can still resolve a cross-file disagreement, because a contract has a
  right answer visible from either side.

THE COST, STATED PLAINLY
  shortener  +63% wall clock (719s -> 1174s)
  taskapipro 3.1x wall clock (3389s -> 10382s, i.e. 56 min -> 2h53m), 27 escalations
  Routing is NOT cheap on hard specs. It is near-free only while the base carries most files;
  once the tail is long, every stuck file drags in a slower member and the 14B dominates. The
  honest trade: on shortener it bought a green build for +8 minutes; on taskapipro it bought
  two stages of progress for +2 hours and still did not finish. Budget accordingly — and note
  the fleet arm was still finding NEW error surfaces when it ran out of rounds, so a larger
  ROUND budget (not a bigger fleet) is the first thing to try on specs of this size.


CONTROL EXPERIMENT — the 5c non-convergence is GONE, and routing was not what fixed it
  5c recorded a live escalation demo on a deliberately weak fleet {1.5B base, 7B} that FIRED
  but never converged: the 1.5B wrote `package stringkit_test` with bare `Reverse(...)` calls,
  and NEITHER model repaired the structural mismatch. `_fix_external_test_package` (builder
  4bdbc6c) shipped afterwards as a deterministic gate for exactly that shape.
  RE-RUN NOW, same weak base, both arms:
      weak base alone   -> GREEN, "deterministic fix in stringkit_test.go",
                           converged after fix round 1, 0 escalations, 11s
      weak base + fleet -> GREEN, identical path, 0 escalations, 8s
  Verified independently: `go test ./...` ok; the file's clause is now `package stringkit`.

  ==> The failure that beat TWO models is now fixed by a gate in one round, and the fleet is
  never consulted. This is the ordering the project should keep: DETERMINISTIC GATES FIRST,
  routing for the residue. Routing's measured wins above (shortener, taskapipro) are wins on
  what the gate chain CANNOT reach — semantic and contract errors where a gate would have to
  guess. Where a single-meaning repair exists, a gate beats routing outright: 11s and no
  second model, versus escalation that previously did not converge at all.
  Corollary for reading the 5c entry: its "rescue is target-bounded" conclusion was about a
  gap that no longer exists in that form.


CORRECTION — "raise the ROUND budget" was WRONG. Tested, falsified, retracted.
  The taskapipro entry above recommended a larger round budget before a larger fleet, on the
  grounds that the 8-round fleet arm was still finding NEW error surfaces when it ran out.
  That recommendation was testable, so it was tested: the identical fleet arm re-run with
  --max-fix-rounds 16.
      fleet, 8 rounds  -> 2/3, 27 escalations, 10382s
      fleet, 16 rounds -> 2/3, 27 escalations, 15537s   (+4300s for NOTHING)
  It ended on "error surface repeats — stopping extension rounds", failing on EXACTLY the same
  two tests: TestListSorted and TestListProjectsSorted, both the sorted-vs-insertion-order
  shape described in FINDING-fresh-failure-triage.txt.

  WHY THE INFERENCE WAS WRONG: "still producing new error surfaces at the budget limit" looked
  like progress being cut short. It was not. The loop was working through a QUEUE of unrelated
  surfaces while the terminal one sat untouched underneath; clearing the queue just exposed
  the same attractor. Progress-in-the-log is not progress-toward-green — the fix loop can be
  busy and stuck at the same time. Extra rounds buy nothing once the remaining failure is one
  the models re-derive identically every time.

  WHAT THIS MAKES THE REMAINING FAILURE: a stable model FIXED POINT, not a budget shortfall.
  The base, go-dev-final AND go-dev-14b all rewrite that test the same wrong way — they seed
  {p2,p1}, compare element-wise against the seed, and never notice that a test whose own name
  is *Sorted* is asserting insertion order. Neither more rounds nor a stronger member escapes
  it. So for this class BOTH levers this project has (rounds, routing) are exhausted, and the
  leverage has to come from somewhere else: the spec/prompt (say explicitly that the expected
  slice must be sorted too), or a gate IF a single-meaning form can be found — which
  FINDING-fresh-failure-triage.txt argues it currently cannot, since the sort key must be
  inferred from another file.

  METHOD NOTE: this cost 4.3 hours of GPU to produce a NEGATIVE result that retracts a
  recommendation published earlier the same day. That is the cheap version of the mistake —
  the expensive version is a recommendation that stays in the record because nobody spent the
  4 hours. Same rule as everywhere else here: a claim nobody has seen fail is not yet a claim.
