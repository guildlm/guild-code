go_review_bench keyword-scoring robustness (2026-07-20)
-----------------------------------------------------------------------------
mlx_review_bench.py scores identify@1 as `any(keyword.lower() in review.lower())`
over ~5 concept keywords per task — one match is a pass. Ran the teeth lens on that:

  - ECHO-DEGENERATE 1/8: wrapped_error_eq lists `%w` as a keyword, and `%w` is in the
    prompt's code being reviewed. A model that merely echoes "%w" passes WITHOUT
    naming the real bug (== vs errors.Is on a wrapped sentinel).
  - GENERIC KEYWORDS that match by chance, not diagnosis: defer_in_loop scores on
    `loop` (any review of looping code says "loop"), double_close on `once`,
    defer_in_loop also on `leak`. `any()` means one incidental hit = a pass.

IMPACT: inflates ABSOLUTE identify@1, but the weakness applies to base and specialist
alike, so it does not bias the A/B direction (same shape as the contamination reading).
The review bench remains a rough, objective signal — just not a tight one.

RECOMMENDATION (do not mutate silently — it would strand any recorded review numbers):
drop the in-prompt/generic keywords (`%w`, `loop`, `once`, `leak`), or raise the bar
from `any()` to ">=2 distinct concept keywords", so a pass requires real diagnosis.

go_test_bench integrity (2026-07-20) — mutation-scored, robust by design
-----------------------------------------------------------------------------
mlx_test_bench scores bug-catch@1 as `_go_test(correct, test) AND NOT _go_test(mutant,
test)` — the model's test counts only if it passes on the correct impl and FAILS on
the planted mutant. That is a mutation-kill by construction (teeth built in). Verified
every task is well-formed by running each REFERENCE test the same two ways:
  - correct == mutant (no real difference): 0/18
  - reference test FAILS on correct (bad reference): 0/18
  - reference test does NOT kill the mutant (un-scorable task): 0/18
All 18 tasks: reference passes correct AND kills the mutant. SOUND.

REFINED THESIS — "the ALGORITHM dominates" is SKILL-DEPENDENT, not universal:
  - GENERATION: the algorithm (retrieval + gates + repair) already carries the base to
    a green backend, so the go-dev generation specialist is REDUNDANT and net-NEGATIVE
    (-6). The MODEL term is ~irrelevant here (matches the pure-model A/B: base and
    specialist fail identically without the algorithm, both ship green with it).
  - TEST-WRITING: the go-test specialist ADDS REAL VALUE (+3, robust MUTATION scoring,
    N=18). Test-writing is a narrower, less retrieval-friendly task, so the specialist's
    trained skill matters — the MODEL term dominates HERE.
  - EDITING (+1, N=6) and BUG-FINDING (-1, weak keyword scoring): inconclusive.

So "capability = model x ALGORITHM" — WHICH TERM dominates depends on the SKILL:
ALGORITHM for generation, MODEL for test-writing. This CORRECTS the earlier flat
"the specialist adds nothing / algorithm dominates so completely the model term is
~irrelevant" (that was measured only on GENERATION).
PRACTICAL: retrieval makes a go-DEV generation specialist redundant — invest the
training budget in the go-TEST specialist, which earns its keep (+3).
CAVEAT: small benches (N=18/8/6); the go-test +3 is the most robust (mutation, N=18);
firm up with larger test/edit benches and n>1 samples.
