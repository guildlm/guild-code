FINDINGS:
  1. THE BOTTLENECK WAS FORM, AND TWO DETERMINISTIC REPAIRS IN THE RIGHT ORDER REMOVE IT.
     The best code model's tests went 2/48 -> 36/48 valid on the reference from stripdecl + goimports
     alone: no prompt change, no training, no judge. Yesterday's "silent branch" conclusion ("the
     bottleneck is judgement; train a test writer") was drawn on a tool with a bug in it and is
     WITHDRAWN. What remains for the 30B (12/48) IS the judgement class (10 wrong assertions), and
     it is a third of what it looked like.
  2. THE REGISTERED PROMPT WAS NOT A LEVER; FOR THE 30B IT WAS A LOSS. With the pipeline fixed,
     "only" scores 31 vs 36 for the default prompt, and its rotate_matrix test lost the property
     that mattered (valid on reference, fails 30B, passes 7B). The 7B is flat (28 vs 27). Telling
     the model what not to write bought nothing the AST repair does not buy better.
  3. THE ROUTER IS AT ITS TONIGHT-CEILING, 46/48, FROM THREE OF FOUR WRITER×PROMPT DRAWS. The last
     point is lru_touch (the Counter task): the 30B's own test PASSES its own wrong Counter (it does
     not probe the bug), and the 7B's tests, though valid, also pass the 30B's version. 47 needs a
     test that reaches the specific defect; that is judgement, and it is the residual.
  4. I MISSED MOST OF MY PREDICTIONS TWICE TONIGHT, BOTH TIMES BECAUSE OF THE INSTRUMENT, NOT THE
     MODEL. First the repair was missing, then it was mis-ordered. Under the corrected order the
     registered predictions about the models would mostly have been right (30B >= 30: yes, 31;
     30B > 7B: yes; 7B >= 24: yes) — recorded as MISSES because the pipeline that ran was the one
     registered. Rule re-earned: test the instrument against a case whose answer you know (a test
     that re-implements the function, with an import only the function uses) BEFORE registering
     predictions on top of it.
