=== DIAGNOSIS: why go-dapt-replay's chat integrity broke (2026-07-19, model-free) ===
Examined the replay corpus datasets/mining/go_dapt_replay.jsonl (38,328 lines):
  - 15% of lines / 13% of CHARS are chat-formatted (matches build_dapt_replay's ~12% --frac target).
  - The chat lines are CORRECTLY formed: full `<|im_start|>system\nYou are GuildLM go-dev...<|im_end|>`
    ... assistant turn ends with ```<|im_end|>\n (im_end count 3 per line). The EOS/stop signal IS
    in the replay data. So the data is NOT the bug.
CONCLUSION: the failure is the FRACTION, not the format. 13% replay char-share was INSUFFICIENT to
keep the chat special tokens / stopping behaviour alive through the DAPT run. build_dapt_replay's own
docstring warns the chat behaviour collapses "after 300-600 steps"; the sibling fused model
`go-dapt600-7b-4bit` implies ~600 steps — right in that danger zone. So 13% replay over ~600 steps
lost the fight.
ACTIONABLE FIX (cheap, concrete): rebuild go_dapt_replay at a HIGHER fraction (--frac 0.25-0.30),
and/or cut DAPT steps below ~400, and/or repeat the replay slice more within one epoch; then re-DAPT
(Kaggle) and re-run behavior_probe FIRST (gate on chat integrity) before trusting any unit-bench
score. The replay recipe is right; there just isn't enough of it. This turns the vague "fix DAPT chat
integrity" NEXT into a single-knob experiment (replay fraction 0.13 -> 0.25).

=== CRITICAL CAVEAT: the specialist-vs-base verdict FLIPS with decoding temperature (2026-07-19) ===
Ran bench_compare against a SERVED BASE (mlx_lm.server, no adapter, temp 0.1 — the PRODUCTION path
the Builder actually uses) to check whether the mlx_bench greedy regression is real:

  harness / decoding              BASE    specialist(go-dev-mixed-v4)   verdict
  mlx_bench     (greedy, temp 0)  39/48   33/48                          specialist −6 (REGRESS)
  bench_compare (served, temp 0.1) 38/48   39/48                          specialist +1 (~TIE)

The 6-point greedy "regression" DOES NOT REPRODUCE under temp 0.1 — there the specialist ~ties/edges
the base (38 vs 39, within sampling noise). So the specialist's apparent regression is largely a
GREEDY-DECODING ARTIFACT: the adapter shifts the distribution so its argmax token is often slightly
worse, but a little sampling (temp 0.1, as in production) recovers it. DECODING TEMPERATURE DOMINATES
the specialist-vs-base comparison on this bench.

CORRECTED CONCLUSION: the mixed-SFT LoRA is NOT a clear net-negative in production — under the temp
0.1 path the Builder uses, it is a wash with the base (not the −6 the greedy bench suggested). The
earlier "LoRA regresses" headline was harness-dependent and is HEREBY QUALIFIED. (temp 0.1 is noisy;
a clean call needs multiple seeded runs — but the direction is clear: greedy over-penalises the
adapter.) The DAPT chat-damage finding is UNAFFECTED — behavior_probe rambling/no-EOS is
temperature-independent, so go-dapt-replay's broken chat integrity stands regardless.
METHOD LESSON: benchmark the specialist at the SAME temperature production uses, and report the
decoding regime — a greedy A/B and a temp-0.1 A/B gave OPPOSITE verdicts here.

Reviewed mlx_bench.py and bench_compare.py for a scoring bug that could bias the
base-vs-specialist A/B this whole study rests on. Found none — the numeric
foundation is sound.

  - IDENTICAL scoring cores: both harnesses use the same runs_green (a task counts
    ONLY if the model's own Go + the hidden test compile and `go test` returns 0,

  - mlx_bench base-vs-adapter A/B is FAIR: base and adapter get the same prompt, the
    same GREEDY decode, the same max_tokens (900), the same EOS registration
    (<|im_end|> added so tuned adapters stop instead of rambling to the cap), the
    same extraction and the same test-run. The ONLY difference is the adapter
    weights. Nothing in the harness advantages one over the other.
  - The greedy (mlx_bench) vs temp-0.1-served (bench_compare) verdict flip is thus a
    genuine DECODING-REGIME effect, not a scoring artefact: the two harnesses differ
    only in decode temperature, backend (local MLX-4bit vs Ollama-served) and
    max_tokens (900 vs 1024) — their scoring is byte-for-byte the same logic.
  - An errored task is a miss in both (numerator unchanged, denominator = all tasks).
  - Fixed one COSMETIC inconsistency: bench_compare's error path lacked mlx_bench's
    `continue`, so an errored task double-appended to the detail list. Scores were
    never affected; the detail output now matches mlx_bench.

VERDICT: no scoring bug; the base~specialist and greedy-vs-served findings stand on
a fair, consistent harness.
